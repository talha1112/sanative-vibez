This document explains how to produce a signed, release-ready Android build for Google Play. It does not contain any credentials, keys, or passwords — those must be generated and held by the client.

## 2. What the client must do (cannot be done without the client's own accounts/credentials)

### Step 1 — Generate an upload keystore

This is a one-time step, and the resulting `.jks` file and its passwords must be kept safe **outside of source control**. If lost, you cannot update the app on Google Play under the same listing without going through Google's key-recovery process.

```bash
keytool -genkey -v -keystore upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias upload
```

You'll be prompted for a keystore password, key password, and identity details (organization name, etc.). Store the resulting `upload-keystore.jks` file somewhere safe and backed up (e.g., a password manager or secure company vault) — **do not commit it to git**.

### Step 2 — Create `android/key.properties`

This file is already `.gitignore`d by the standard Flutter template pattern — verify this repo's `.gitignore` excludes `key.properties` and `*.jks`/`*.keystore` before creating it (see §4 below). Create `android/key.properties` (not tracked in git) with:

```properties
storePassword=<your keystore password>
keyPassword=<your key password>
keyAlias=upload
storeFile=<path to your .jks file, e.g. /Users/you/keys/upload-keystore.jks>
```

The existing `android/app/build.gradle` is already wired to read this file automatically — no code changes are needed once this file exists.

### Step 3 — Build the signed App Bundle

```bash
flutter clean
flutter pub get
flutter build appbundle --release
```

Output: `build/app/outputs/bundle/release/app-release.aab`

This `.aab` (Android App Bundle) is the file uploaded to Google Play — not an `.apk`.

### Step 4 — Verify signing (optional but recommended)

```bash
jarsigner -verify -verbose -certs build/app/outputs/bundle/release/app-release.aab
```

Should report the bundle as signed by your upload key.

## 3. Uploading to Google Play Internal Testing

This requires **client-owned access** to:
- A Google Play Console account (Developer account, $25 one-time fee if not already registered)
- The app's listing created in Play Console (or permission to create one)

Steps once access is available:
1. In Play Console, create the app listing (if not already created) under the client's developer account.
2. Go to **Release → Testing → Internal testing** → **Create new release**.
3. Upload `app-release.aab`.
4. Fill in release notes (can be minimal for internal testing, e.g., "Version 1.0.0 — initial internal test build").
5. Save and review, then **Start rollout to Internal testing**.
6. Under the Internal testing track, add tester email addresses (individually or via a Google Group), then share the generated **opt-in testing link** with testers.
7. Testers accept the opt-in link, then install the app from the Play Store (it will show as an internal test version).

**Note on Play App Signing:** Google Play strongly recommends enrolling in "Play App Signing," where Google re-signs your app with its own key for distribution while you keep your upload key. This is configured once in Play Console when the first release is uploaded and does not require any code changes.

## 4. Protecting signing credentials — checklist

- [ ] `android/key.properties` is never committed (confirm `.gitignore` excludes it)
- [ ] The `.jks`/`.keystore` file is never committed
- [ ] Both are stored in a secure, backed-up location the client controls (password manager, secure vault, or Play App Signing after initial upload)
- [ ] Passwords are not shared over plain email/chat — use a password manager's sharing feature or a secrets manager
- [ ] Only people who need to produce release builds have access

## 5. Debug vs. Release

- **Debug builds** (`flutter run`, `flutter build apk --debug`) are signed automatically with a local debug key generated by the Android SDK. These are for local development only and cannot be uploaded to Google Play.
- **Release builds** (`flutter build appbundle --release` or `flutter build apk --release`) use the signing config in `android/app/build.gradle`, which requires `android/key.properties` to exist as described above. Without it, `build.gradle`'s existing fallback logic will sign the "release" build with the **debug key** instead — this will build successfully but will **not** be accepted by Google Play, and must not be distributed as a final release.

## 6. What still requires client action

- Generating the upload keystore (Step 1) — this creates a credential that must be controlled by the client, not by a developer/agency, since losing access to it can affect the client's ability to update the app later.
- Google Play Console account access/ownership.
- Creating or granting access to the app's Play Console listing.
- Deciding on Play App Signing enrollment (recommended, done in Play Console).
